# 视频清晰度排查与导出画质改进

日期：2026-09-09。Conductor 基线 `9503e448272e4c6df0942e2c08b05d50d883868e`；
Bridge SDK 基线 `d529357119f257e7fec7b7aa184d6b7d09e000ff`。
本轮修改位于本地 Bridge SDK 工作区，没有发布客户端或部署设备。

## 结论与证据边界

已检查原生采集、硬件分眼编码、SDK 和 Desktop 的成片生成代码，并探测本地真实录制。
没有发现 1080p 被录成 720p、或完整双目被缩成 1920×1080 的情况。
现有分眼原片为每眼 1920×1080，左右拼接成片为 3840×1080。

导出会再次有损编码，可以减少这一层损失。但人物样片的原始设备 H.264
已经出现偏软细节，不能把所有模糊都归因于客户端。原片仍然经过相机 MJPEG
与设备 H.264 两次编码；没有同步原始 MJPEG/RAW 对照，无法分离镜头、曝光、
相机 ISP/JPEG 和设备 H.264 各自的损失。

1920×1080 表示整眼图像的像素数，不能证明焦点正确或小目标拥有充分细节。
广视野样片里人脸仅占大约百像素，放大人脸不会得到整幅 1080p 的细节。

## 各环节核查

| 环节 | 证据 | 判断 |
|---|---|---|
| V4L2 采集 | `native/src/v4l2.rs` 在 S_FMT 后检查尺寸和格式必须完全匹配；生产双目 3840×1080 MJPEG | 没有静默降分辨率路径 |
| 分眼 | `src/rp_ylx/hobot/ylx_stereo_pipeline.c:split_eye` 按行复制 Y/UV，各复制 1920 像素 | 不经过空间缩放 |
| 录制编码 | 每眼 H.264；配置码率 8192 kb/s；I/P、GOP 30、无 B；min QP 20，initial 24，intra 22 | 有损。min QP 是下限，不能理解为每帧固定 QP 20；单改码率不保证实际码率或质量 |
| 分段 MP4 / 下载 | 已有原件哈希验证；MP4 存储压缩视频包，下载保留字节 | 分段封装和完整字节传输不会再引入编码损失 |
| SDK / Desktop 拼接 | `hstack`，保留尺寸；H.264 veryfast/CRF 20，HEVC medium/CRF 22 | 再次有损编码，存在可优化空间 |
| Desktop 另存 | 默认 H.264/零补偿有整文件复制路径；另存 HEVC 会重编码 | 已有 H.264 再转 HEVC 多一代损失，不应作为提升清晰度的方法 |
| 原生预览 | `native/src/preview.rs` 发布传入 JPEG 字节；本次 HTTP 取得 JPEG 3840×1080、265459 字节 | 未降空间分辨率；客户端显示尺寸仍需按反馈场景核查 |

本地 ffprobe：旧人物原片左眼 1920×1080、约 9.59 Mb/s；新版长录第一段左眼
1920×1080、约 7.85 Mb/s；人物成片 H.264 与 HEVC 均为 3840×1080。
不同场景、时长、编码代际的码率不能直接当成画质排名。

9 月 8 日固件已经有 I/P 和 QP 优化，本次不是首次发现或重新实施这些改动。
当天同输入硬件实验的 QP20→QP18 收益较小，详见
[此前硬件编码报告](2026-09-08-hardware-encoding-optimization.md)。
需要用相机直接输出的 MJPEG 做下一轮硬件实验，才更接近实际录制损失。

## 本次受控导出实验

使用 SDK 当前实际的 FFmpeg 参数生成器与其捆绑 FFmpeg。
左右眼各 120 帧，输出均为 3840×1080；无音频，固定比较时间轴为 30fps。
逐眼裁剪、按帧序对齐，将 full-range 原片和 limited-range 成片转换到相同数值范围后计算 SSIM。
每项确认恰好比较 120 帧。SSIM 只衡量相对于已压缩原片的变化，不能代表镜头分辨率、
相对于传感器 RAW 的质量或人体感知清晰度百分比。
方法参考 [FFmpeg SSIM 文档](https://ffmpeg.org/ffmpeg-filters.html#ssim)
与 [FFmpeg 编码器文档](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb)。

人物运动片段：会话 `01a0810a-9719-785c-9000-9a6240051023`，原片帧 360–479。
该会话使用旧全 I 固件，包含人物拍手、衣服与室内背景。

| 导出模式 | 平均左右眼 SSIM | 4 秒视频大小（十进制 MB） | 本机编码时间 |
|---|---:|---:|---:|
| H.264 标准 veryfast / CRF20 | 0.989516 | 10.006 | 3.43 s |
| H.264 高画质 medium / CRF18 | 0.992754 | 14.142 | 8.81 s |
| HEVC 标准 medium / CRF22 | 0.987146 | 5.938 | 12.43 s |
| HEVC 高画质 medium / CRF18 | 0.991542 | 11.337 | 16.57 s |

H.264 高画质在这段中增加约 41% 体积、编码时间约 2.57 倍。结果不应外推为所有内容的固定比例。
H.264 与 HEVC 的相同 CRF 数字也不表示相同视觉质量。

新版 I/P 素材另测：会话 `01a081a4-7b42-765f-84b2-0e3d43edc1d8`，前 120 帧，
画面主要是静态天花板。H.264 标准/高画质平均 SSIM 0.996028/0.996954；
HEVC 标准/高画质 0.994588/0.995402。这组低细节内容的高分不代替人物场景验收。
已有完整 H.264 成片的同帧 SSIM 0.996496。完整成片和 4 秒实验的编码上下文、GOP、
实际 PTS 不同，不能要求指标完全相等。

## 已落实的改进

Bridge SDK `ExportOptions` 新增 `video_quality="standard" | "high"`。
标准保持原有行为；高画质对 H.264/HEVC 都使用 medium/CRF18，不缩放图像。
终端 P / 导出设置提供画质选择，重新打开、取消、批量导出均保留正确选项。

设置写入原有导出收据，改变画质会重新导出并保留旧结果备份；旧收据缺少字段时按标准处理。
LAN 与卡片模式共用选项传递。`retain_sources=True` 可保留字节完全一致的原始素材，
但拼接 MP4 仍是有损编码，已修正文档里易造成“可无损重导出”误解的描述。

验证：导出设置、终端、集成导出、真实媒体专项共 89 项通过；增加实际画质切换缓存重建
断言后，相关 5 项再次通过。Ruff 和 `git diff --check` 通过。
两个真实场景、两个编码器、两个画质档共八次编码完成，每项左右各 120 帧。

## 现场状态与下一步

本次设备 `192.168.110.248` HTTP `/api/v4/device` 返回固件
`df9c7085f8f5c4f92434a6f3d25b95f836c4aaff`；`capture/status` 返回 idle、camera connected、
camera_focus null（不能据此断言镜头一定失焦或具有可用自动对焦）。
SSH 公钥认证失败；随后 `/camera/focus` 与 `/preview` 请求曾连接被拒绝。
发现另一工作流正在升级设备，等待其恢复后只读复查：设备已为 `9503e44`，相机 connected。
`/preview` 返回 3840×1080、265459 字节的原始 JPEG；`/camera/focus` 返回 404，
明确错误码 `camera_focus_unsupported`，说明当前相机没有可读取的焦距控制。
这不证明失焦，也不证明所有厂商私有对焦机制均不存在；现有软件接口无法用来做焦点调节。
该 JPEG 的场景与历史人物录制不同，不能用两者直接计算采集/编码损失。
本轮未修改曝光、焦点、固件或录制参数；并行部署不属于本轮画质改动。

建议安排可控的现场目标后按以下顺序测量：

1. 同一静态细节目标/测试卡，取相机 MJPEG 与对应 H.264，按相同眼和像素位置比较。
2. 测试工作距离、镜头洁净情况、固定/自动对焦能力，并对静止与运动目标分别检查。
3. 在相同照明下比较自动曝光与较短曝光；同时记录增益、噪声和闪烁，不能盲目统一曝光值。
4. 只有编码前明显更清楚时，才以该 MJPEG 输入测试录制码率、QP、实际码率、丢帧及温度。
5. 原片清楚而界面不清楚时，再查播放器缩放。3840 宽的双目图缩到 1920 宽窗口时，
   每眼只显示约 960 像素宽；应在原尺寸下检查单眼，而不是从缩小的双目窗口判断原片分辨率。
