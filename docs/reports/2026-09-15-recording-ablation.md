# 录制修复消融实验

本轮完成本地短时故障注入和新旧实现对照。检查点、恢复流程、双眼配对、音频恢复、下载索引、失败后重试均呈现独立作用；写盘解耦明显缩短受控阻塞下的输出缓冲占用时间。实验不证明 .180 的相机源缺帧已解决，也不提供真实设备长录制失败率。

用户此前要求停止长时间验证，随后要求对本次大量修改做消融。本轮采用本地实验，没有切换 .180 固件或产生设备测试录制。实验源码变体、合成数据与结果均放在独立证据目录，未在生产实现加入实验开关。

## 版本、方法与边界

- 修复前参考：f89a3b7aa5e455f62dea6984c266b65d3c0d3917。
- 完整修复源码：379d7e402e5aea39da7e263319db3b06863bc904，录制实现与设备上的 95bd606 相同，另含来源标记和报告收尾。
- 环境：Linux x86_64、Python 3.13.13、GCC 11.4.0、Rust 1.93.1。
- 每次对照保持同一输入和故障条件，移除单个机制或替换为真实旧函数；相互依赖的机制额外采用组合对照。普通用例重复 5 次，轮换执行顺序。管道阻塞重复 3 次；双眼配对穷举全部 252 种受测合法顺序。
- Python 恢复用例调用真实 recorder/coordinator/recovery/download 代码，编码器替身生成可做哈希校验的文件；这些文件不是可播放视频。没有用其耗时估计实机编码、恢复或导出性能。
- C 写盘实验直接提取真实新旧输出线程函数和新版写盘线程函数编译运行，替换的是硬件编解码与 muxer 接口。延迟来自明确注入的阻塞，输出缓冲是适配器内存，不是实机 VPU。
- 原生重试实验在独立源码快照中运行真实 Rust Runtime，模拟故障后仍存活的 IMU worker；对照回退的是旧版是否清理 worker 的条件。
- “可下载”指清单列出的全部文件能通过 coordinator 普通文件读取接口打开并校验 SHA256，含恢复回执。本轮没有重新运行 Bridge 媒体合成或浏览器 UI。

重复实验检验受控场景下结果的一致性，不是对用户实际故障概率的抽样估计。

## 1. 分段恢复的必要条件与交互

固定输入：32 帧；每段 3 帧，10 对完整双目分段；第 11 段不完整；音频为真实 PCM 样本配合合成的有效时钟观测。每组复制同一个输入目录，模拟进程失去内存状态后的启动恢复。

| 变体 | 自动发布的完整段 | 可用帧数 | 音频采样帧数 | 清单文件全部可下载 | 重复结果 |
| --- | ---: | ---: | ---: | --- | --- |
| 完整修复 | 10 对 | 30 | 47,520 | 是，24/24 | 5/5 一致 |
| 去掉分段检查点 | 0 | 0 | 0 | 无发布结果 | 5/5 一致 |
| 去掉持久录制上下文 | 0 | 0 | 0 | 无发布结果 | 5/5 一致 |
| 关闭启动恢复 | 0 | 0 | 0 | 无发布结果 | 5/5 一致 |
| 同时去掉检查点、关闭恢复 | 0 | 0 | 0 | 无发布结果 | 5/5 一致 |
| 去掉音频检查点 | 10 对 | 30 | 0 | 是，23/23 | 5/5 一致 |
| 回退日志文件索引 | 10 对 | 30 | 47,520 | 否，23/24，回执 404 | 5/5 一致 |
| 去掉音频检查点并回退日志索引 | 10 对 | 30 | 0 | 否，22/23，回执 404 | 5/5 一致 |
| 缺音频检查点时使用旧清单 schema | 0 | 0 | 0 | 无发布结果 | 5/5 一致 |

“去掉分段检查点”通过删除该机制的持久文件实现，模拟旧实现只有内存完成记录；这不是物理断电实验。“去掉录制上下文”移除新增的配置、会话计划和时钟原点。“关闭启动恢复”只替换 coordinator 的恢复调用，其他逻辑保持完整修复版本。

检查点与恢复的 2×2 对照显示两者互相依赖：只有两者同时存在才自动发布前段。独立移除录制上下文同样无法恢复。由此支持保留三者，不能仅保留分段视频文件而去掉元数据和恢复流程。

音频检查点与日志索引的 2×2 对照显示：音频检查点负责保留音频，日志索引负责完整下载，二者互不替代。没有音频检查点时使用旧 schema，与“去掉音频检查点”组相比只改变 schema；它不接受“用户要求录音但因中断未恢复音频”的结果，连视频前段也无法发布。因此 schema 修改是音频降级兜底的必要配套。

所有 60 次恢复用例均检查了原始视频、WAV、帧索引和 IMU 索引的 SHA256，恢复前后原始内容保持一致。

## 2. 完整性故障控制组

这些是故障控制组，不把“换了一种输入损坏”算成关闭某个修复。

| 输入故障 | 完整修复的结果 | 重复结果 |
| --- | --- | --- |
| 第 10 对右眼文件损坏 | 只发布前 9 对、27 帧；音频截到 42,720 个采样帧；全部文件可下载 | 5/5 |
| 帧索引在第 10 对内截断 | 只发布前 9 对、27 帧；音频截到 42,720 个采样帧；全部文件可下载 | 5/5 |
| 音频时钟观测倒退 | 保留 10 对、30 帧视频；音频明确标记未恢复；全部文件可下载 | 5/5 |

结论：恢复选择连续完整前段，尾部损坏不会扩大为整次数据不可用；无法确认有效的音频不会阻止有效视频恢复。

## 3. 写盘解耦

每次输入 60 个 64 KiB 压缩包，适配器约每 1 毫秒提供一个包。新旧实现收到相同包；第一笔 muxer 写入注入 250 毫秒阻塞。输出缓冲释放后立即被覆写，写盘端逐包校验内容，以确认异步队列真正持有独立副本。

下表为 5 次实验中“单次最大缓冲持有时间”的中位数；不能将该指标称为整机吞吐或 VPU 实测延迟。

| 变体 | 写入阻塞 | 最大缓冲持有时间中位数 | 输出线程完成时间中位数 | 写入结果 | 压缩包队列峰值 |
| --- | ---: | ---: | ---: | --- | ---: |
| 旧同步路径 | 0 ms | 0.0525 ms | 65.56 ms | 60/60，内容一致 | 无额外队列 |
| 完整修复 | 0 ms | 0.0222 ms | 63.89 ms | 60/60，内容一致 | 64 KiB |
| 旧同步路径 | 250 ms | 250.0855 ms | 315.48 ms | 60/60，内容一致 | 无额外队列 |
| 完整修复 | 250 ms | 0.0385 ms | 65.62 ms | 60/60，内容一致 | 3.75 MiB |
| 完整修复，但队列容量降至 8 帧 | 250 ms | 0.0292 ms | 9.75 ms，提前报错退出 | 8 帧落盘，下一帧明确拒收 | 512 KiB |

阻塞场景下，旧路径 5 次最大缓冲持有时间为 250.0821–250.0865 ms；新路径为 0.0333–0.0643 ms。新路径仍需等写盘线程完成，整体排空约 253 ms，不能把约 66 ms 的输出线程结束时间当作文件已经全部写完。

容量降至 8 帧的组，5 次均恰好拒收 1 帧并失败，已排队 8 帧完整写出且内容正确。这是提前失败，不是性能提升。实验支持有界队列能吸收本场景的短时阻塞，也支持容量耗尽时明确报错；没有证明当前每眼 32 MiB/480 帧是最佳容量。

## 4. 双眼封段记录

直接编译真实 ledger_record 新旧函数。每只眼分别完成 5 段，保持每只眼内部序号递增，穷举左右眼交错的全部 C(10,5)=252 种完成顺序。

| 指标 | 旧版每眼单槽记录 | 完整修复 |
| --- | ---: | ---: |
| 5 对分段都能完整报告的顺序 | 32/252 | 252/252 |
| 所有顺序累计报告的分段对数 | 772/1,260 | 1,260/1,260 |
| 所有顺序累计可形成连续前段的对数 | 332/1,260 | 1,260/1,260 |

旧逻辑在快眼连续完成多段时覆盖较早的完成记录。这个问题即使没有相机缺帧也存在，会直接影响恢复可用前段。应保留按分段序号配对及连续发布逻辑。

32/252 是这组穷举事件顺序的覆盖结果，不是实机成功率。

## 5. 分段封存错误处理

提取真实 segment_seal 新旧函数；文件和目录使用真实临时目录，muxer、MP4 修补和 fsync 由适配器分别返回故障。

| 注入条件 | 旧逻辑 | 完整修复 |
| --- | --- | --- |
| 无错误 | 报告段完成 | 报告段完成 |
| muxer 关闭失败 | 已标记失败，但仍报告段完成 | 标记失败，不报告完成 |
| MP4 时长修补失败 | 已标记失败，但仍报告段完成 | 标记失败，不报告完成 |
| 文件 fsync 返回 EIO | 未标记失败，仍报告段完成 | 标记失败，不报告完成 |
| 目录 fsync 返回 EIO | 旧实现没有这次同步，仍报告段完成 | 标记失败，不报告完成 |

结论：这些检查防止“未可靠封存的段被记为完成”。它们是恢复检查点可信的前提，不应因为正常路径没有触发错误而删除。本实验不验证真实断电后的存储持久性。

## 6. 失败后重试、进度和结束信号

| 机制 | 消融结果 | 完整修复 |
| --- | --- | --- |
| 失败后 IMU worker 清理 | 旧条件下 5/5 次遗留 worker，下一次录制均报 invalid_state | 5/5 次清理完成，下一次录制成功开始 |
| 失败前保存原生进度 | 实际写入 3 帧，去掉进度快照后 5/5 次显示 0 帧 | 5/5 次显示 3 帧 |
| 结束时写终止包改为关闭管道 | 满 64 KiB 管道、读端不消费时，旧终止包写入 3/3 次在 300 ms 看门狗到期仍阻塞 | EOF 关闭 3/3 次返回，操作约 0.0017–0.0019 ms |

重试组运行真实 Rust Runtime；进度组只移除真实 _abandon_encoder 中保存进度的代码块，其他逻辑相同。进度快照修复显示准确性，不增加已经写入的媒体数量。

结束信号组运行真实操作系统管道的对应写入/关闭操作，不运行完整编码器结束流程；它证明旧写入可能卡在超时等待逻辑之前，不能把关闭 fd 的微秒耗时等同整个录制停止耗时。

## 保留建议与未覆盖项

建议保留写盘队列和线程、分段持久检查点、启动上下文、恢复发布、双眼配对、封存错误检查、音频检查点和降级 schema、下载日志索引、失败后 worker 清理、失败进度快照及 EOF 结束方式。它们在各自触发场景中有明确独立作用。

队列容量、检查点提交频率、源输入稳定性需要另做性能或实机对照才能评价。本轮没有得到足以减少队列容量、降低检查点可靠性或放宽缺帧规则的证据。

诊断统计、相机最近 64 帧耗时观测、UI 恢复提示、OpenAPI 枚举和源码来源标记属于可观测性、界面或契约配套。本轮没有分别关闭这些展示/统计项测量开销，也没有做 UI 渲染对照，因此不把它们列为“已证明降低丢帧”的修改。

失败时主动排空已接收尾段、Rust 音频检查点生产端、Rust 下载日志收集器未单独做完整开关对照：本轮音频/日志实验检验恢复消费端和 Python 普通下载路径，已有实机恢复与导出记录可作补充证据，但不是这些项各自的消融结果。

.180 此前出现的 source_gap=2、queue_rejected=0 仍然是未解决事项。本轮实验不能确定更早的缺口 43/71 由哪一个原因造成，也不能声明相机、USB 或驱动输入已稳定。
