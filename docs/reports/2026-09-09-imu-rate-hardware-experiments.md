# 2UQ2 标称 IMU 800/400 Hz：.248 真机读取实验与实现路径

日期：2026-09-09。设备：`192.168.110.248` / `YLX-1C7447D1`。相机：`2UQ2`，USB `1bcf:0b15`，`bcdDevice=0701`，USB 连接速度 480 Mbit/s。设备业务版本始终为 `9503e448272e4c6df0942e2c08b05d50d883868e`。

> **同日第二轮追加调试：** 用户进一步要求恢复标称采样率。第 11 节记录 USB 请求追踪、1/2/4/8 路并发读取、UVC 元数据、原始 JPEG 和手动短曝光实验。短曝光后视频实收达到约 120/210/556 fps，但 IMU 接口仍没有达到目标。**截至本轮结束，800/400 Hz 完整输出尚未恢复或证实，业务采集器未修改、未部署新固件。** 第一轮“没有改变曝光、未做并发/内核追踪”的描述只适用于第 1–10 节所述阶段。

本轮用户授权真机实验，承接此前“只做调研、不改业务代码”的约束。实验使用 `/tmp` 中的独立 Python/C 探针；临时停止服务并切换视频模式后恢复。没有修改业务代码、部署候选版本、创建业务录制、写入未知 XU 控制或操作 TRIG。

## 1. 结论与对前一份报告的修正

**已经找到一个明确的软件过滤错误，但尚未证明当前接口能够完整输出加速度 800 Hz、陀螺仪 400 Hz。**

1. **同一视频帧计数器下，IMU 载荷仍在更新。** 旧采集器只在前三字节变化时返回数据，因而丢掉同一帧号内后续读到的 IMU 载荷。旧录制约 59.4 包/s、118.8 行/s 是软件接受并保存的速率，不是相机 IMU 发布上限。
2. **保存每次 GET_CUR 响应，实测约 203 次/s、406 个六轴数据槽/s。** “槽”指返回格式中的一组六轴字段；没有独立样本序号、有效位和采样时刻，不能将它直接称为 406 个新样本/s。
3. **当前顺序读取路径不足以完整输出 800 Hz 加速度。** 每次只有两组三轴加速度，约 203 次读取最多承载约 406 个加速度向量/s。即使每组都是新样本，也不到 800。400 Hz 陀螺仪在纯数量上勉强容纳，但重复值、未知两组语义和缺少时间戳使完整性无法验证。
4. **瓶颈不只在应用层循环。** Python 改原生 C、去掉预览解码、更换视频格式及分辨率，都没有把有效顺序读取吞吐提升到 400 次/s。这里定位的是整个 XU 控制读取路径的实测限制，尚不能区分相机 MCU、USB 控制传输调度与内核驱动各自的耗时。
5. **优先向厂商确认 FIFO/批量读取协议。** 可以保留芯片内部 800/400 Hz，以 50–100 次/s 的批量传输送齐样本。是否已有隐藏配置可开启这种模式、或必须修改相机固件，现有资料不能确定。

前文 [YLX 2UQ2 IMU 研究](2026-09-09-ylx-2uq2-imu-study.md) 已加醒目修正。原有离线包数、计数器跳变和主机时间统计仍成立；把它们解释为硬件输出上限的推断不再成立。

## 2. 如何区分“达到采样率”

| 层次 | 需要确认的内容 | 本轮状态 |
| --- | --- | --- |
| 芯片内部 ODR | IMU 型号、ODR 寄存器实际值；800 Hz 加速度、400 Hz 陀螺仪 | 只有厂商描述，尚未读到芯片证据 |
| MCU 读取完整性 | 按数据就绪/FIFO 取出每个样本，是否发生覆盖、抽取或平均 | 未知 |
| USB 输出完整性 | 每轴传出的样本数量、独立序号、溢出状态与采样时间 | 当前 27 字节格式不能证明 |
| 上位机接受率 | GET_CUR 返回的数据有没有被软件丢掉 | 已证明按帧号过滤会丢载荷 |
| 落盘与融合可用性 | 每样本时间戳、单位、坐标、无丢失验证、视频时钟关联 | 本轮未修改生产实现，尚未完成验收 |

不能用“每秒写 800 行”“插值为 800 Hz”“调用 ioctl 800 次”替代这些条件。静止时两个独立样本可能数值相同；同一旧包的两个槽位也可能不同，反复展开会制造大量数值跳变。因此本报告不使用数值去重率作为真实采样率。

## 3. 实验方法与证据

### 3.1 直接记录每次响应

使用已知的 `UVCIOC_CTRL_QUERY`，unit 3、selector 1、GET_CUR、固定 27 字节。每次保存：

```text
[host_read_start_monotonic_ns, host_read_end_monotonic_ns, payload_hex]
```

前三字节按大端 uint24 解码；剩余 24 字节按大端 12 个 int16 解码。不按前三字节过滤，不为返回内容生成虚构的 ADC 时间戳。

Python 探针先验证设备 idle，并请求现有服务预览以确保视频流运行。C 探针以 `-O2` 编译，在内存中保存全部响应，实验结束再写 JSON，避免逐条 JSON 编码和写盘干扰热循环。独占视频实验先停服务，由 `v4l2-ctl --stream-mmap=4 --stream-poll --stream-to=/dev/null` 接收视频，不做解码；每个模式预热 2 秒再测量。

统计口径：`N / (最后一次读取结束 - 第一次读取开始)`。计数器变化率按相邻观测中发生变化的次数计算，有首尾观测误差，并非长时间帧时钟拟合结果。各组实验为 5–15 秒的定位实验，不等于连续生产录制压力验收。

### 3.2 可复核的同帧号变化例子

连续读取中相邻三次响应如下。为了看清字段，前三字节与其余字节之间加了空格；原始文件中没有空格。

```text
070e1b 005b0eea069b00070003001600320ee00694000800050012
070e1b 004b0eff06a100070006001500370f08069e000700060015
070e1b 002d0eec06c2000800010015003c0ee306af000800010015
```

帧号均为 `0x070e1b`，24 字节载荷持续变化。第一、第二次读取起点分别为 `11300275176425`、`11300279065328 ns`；不是人工复制或插值产生的记录。

15 秒连续实验共读 3,048 次。相邻响应中 2,155 次帧号没变，**这 2,155 次的 IMU 载荷全部变化**。按旧逻辑，这部分响应全部被过滤，占相邻响应的约 70.7%。这直接否定“帧号相同就没有新 IMU 信息”的假设，但单独一次载荷变化不能证明其两个槽位都代表新采样。

在 640×240 模式中，IMU 包前三字节的观测变化率约 79.64/s；640×480 YUYV 模式约 29.91/s，与实际收帧频率接近。与此同时，XU 读取仍约 200 次/s，重复帧号内的 IMU 载荷仍变化。这进一步支持“前三字节是帧相关计数器，并非每个 IMU 样本的计数器”的解释。

### 4.1 单次读取耗时

| 条件 | p50/ms | p95/ms | 最大/ms |
| --- | ---: | ---: | ---: |
| Python 紧循环、生产预览 | 4.647 | 5.550 | 6.521 |
| C 紧循环、生产预览 | 4.778 | 5.636 | 6.629 |
| C 紧循环、只接收 MJPG 60 | 4.789 | 5.638 | 6.676 |
| C 紧循环、无视频 | 1.014 | 1.035 | 1.409 |

有视频时约 4.92 ms/次的平均请求周期，把当前顺序读取压在约 203 次/s。目标 400 次/s 要求平均周期不超过 2.5 ms。单纯删掉主机 sleep、换 C、取消解码没有达到这个要求。

这些结果尚不能证明 USB 总线物理带宽不足，也不能证明相机硬件不可改进。后续若需要定位到驱动/设备，可用 USB 请求提交/完成追踪分解 ioctl 等待时间，结合厂商 MCU 的 I²C/FIFO 日志确定真正的耗时位置。本轮未做内核追踪、并发多 FD 读取或驱动改造，203 次/s 是已测路径的结果，不是所有可能接口的绝对上限。

### 4.2 无视频的高速响应为什么无效

无视频时 4,915 次响应完全相同，帧计数器变化数为 0，完整载荷变化数也为 0。单包内部两组值仍可能不一样，因此机械展开两组、再统计相邻数值变化，甚至会得到超过千次/s 的假象。这一对照证明必须先确认数据流在推进，不能以查询速度或数值变化数量作为采样率证明。

### 4.3 暂停读取是否能补回历史

另做约 15 秒的间歇实验，周期性暂停约 100 ms。恢复后的帧号跳变为 6 或 7，后续连续读取的计数器增量主要为 0 或 1，未见从旧帧号逐条补回的过程。

这说明**当前 27 字节读取方式没有表现出按历史帧排队回放的行为**，更接近读取当前发布值。但包内没有独立样本编号，不能据此证明芯片没有 FIFO，也不能排除有尚未启用的 FIFO 接口或包内历史样本。

## 5. 为什么 406 个数据槽不能宣称完整 400 Hz 陀螺仪

生产预览 + C 实验中，同包两组三轴加速度完全相等的比例约 5.61%；两组三轴角速度完全相等的比例约 63.78%。这与“两组总是两次独立且不同的六轴采样”的简单解释不符，却不足以反推实际 ODR。

可能性包括：相机 MCU 在两个时刻读取了加速度，而期间角速度输出寄存器未更新；两组中含复用/旧值；芯片滤波、量化及静止条件导致独立样本相同；封包时从多个不同步缓存取值。现有数据无法区分这些机制。

因此：

- 不用相同三轴值判断重复样本；不同比例也不能证明 800:400 的更新关系。
- 不把两组强行均分到每帧内，或强行分配 1.25/2.5 ms 间隔。
- 不把主机请求中点当作采样时刻。当前 4–6 ms 的读取时间区间，本身已经大于加速度 1.25 ms 的标称采样间隔；数据在相机缓存中滞留多久还未知。
- 只有各传感器的独立样本序号/数据就绪证据、采样时钟和溢出状态，才能判断是否真的送齐了 800/400 Hz。

## 6. 接口发现：有无现成高速开关

相机描述符的 IMU XU 为 unit 3，GUID `D5C2F42C-1808-4D9F-BE56-753E271C9244`，声明 3 个控制，bitmap `07 00 00 00`。本轮只读查询这些控制的长度与 GET/SET 能力：

| Unit | Selector | GET_LEN 原始值 | 长度/字节 | GET_INFO |
| ---: | ---: | --- | ---: | --- |
| 3 | 1 | `1b 00` | 27 | `03` |
| 3 | 2 | `01 00` | 1 | `03` |
| 3 | 3 | `01 00` | 1 | `03` |

`GET_INFO=03` 仅表示支持 GET 和 SET 请求，不说明写入哪个值能开启 FIFO、改变 ODR 或启用外触发。GET_LEN 需要按小端解码，GET_CUR 缓冲区必须匹配控制长度；把 selector 1 的请求长度直接改成 54/108 字节不是有依据的批量读取方法。[Linux UVC 官方文档](https://www.kernel.org/doc/html/latest/userspace-api/media/drivers/uvcvideo.html)

另有 unit 4，GUID `63610682-5070-49AB-B8CC-B3855E8D221D`，声明 25 个控制，bitmap `ff ff 77 07`。这些私有控制的语义尚未取得。未对 unit 4 做未知载荷读取/写入，也未对 selector 2/3 发 GET_CUR 或 SET_CUR。

尝试通过 USBDEVFS_CONTROL 发送同一已知 GET_CUR 请求时返回 `EBUSY (errno 16)`；未解除内核对接口的占用，因此没有获得能和 UVC ioctl 比较的直连 USB 吞吐数据。不能把该失败解释为另一条路径性能更好或更差。

本轮公开资料检索未定位到可确认对应此相机版本的厂商 Linux SDK 或完整 XU 协议。用户说明中的“可编译调用的库”仍是关键线索。现有元数据不能证明“没有高速接口”，只能说明尚未找到并验证它。

## 7. 达到标称采样率的具体路径

### 7.1 先修主机的观测模型，保留已经能读到的信息

这是由本轮直接证据支持的软件工作，尚未实施：

1. `native/src/imu.rs::read_fresh_packet` 和 `src/rp_ylx/imu/uvc_xu.py` 不能再按前三字节是否变化来决定是否接受 IMU 响应。高频采集应保留每次响应和读取区间，再单独标记载荷相同/帧号重复等诊断信息。
2. 帧计数器、主机响应序号、包内槽位索引需要分开。视频帧号相同在新模型中是正常现象，不能触发 `timestamp_stalled`。Rust `CounterUnwrapper` 和 Python `imu/time_sync.py` 都有零增量错误路径，不能只删除采集器的一条 `if`。
3. 视频帧计数器的展开和拟合按独立帧观测处理；不要把同帧号的所有读响应都当成新的独立帧时间锚点。没有厂商样本时序信息之前，给数据保留主机观测时间和“采样时刻未知”状态。
4. 错误指标拆成查询失败、帧号未观测位置、相同载荷比例、设备报告溢出/样本缺失。设备没有样本计数时，样本丢失数应为未知，不能继续用硬编码 0 表示完整。
5. 生产录制、Python 备用读取、正在开发的 idle IMU 路径及下游导出/融合需要一起审查，保持单一采集所有者，避免两个线程争读未来的消费型 FIFO。

实验探针已证明约 406 槽/s 的接收可能性，是旧保存速率约 118.8 行/s 的 **3.4 倍**。把这一收益带入生产还需实现上述模型和验证长录制、CPU/写盘开销、错误恢复及读者兼容性，不能直接把探针数字当作部署后的承诺。

### 7.2 完整 800/400 Hz 优先采用相机 FIFO 批量输出

不含时间戳和协议头，目标原始数据量是：

```text
加速度：800 × 3 轴 × 2 字节 = 4,800 字节/s
陀螺仪：400 × 3 轴 × 2 字节 = 2,400 字节/s
合计：7,200 字节/s = 57.6 kbit/s
```

该数据量很小，但当前格式每次固定两组六轴值：约 203 次/s 只有约 4,877 字节/s 的轴值载荷，而且为相等的加速度/角速度槽数，无法直接表达 800:400 的两个独立流。若仍用此格式，800 Hz 加速度至少需要 400 次/s，且每次两组必须确认为不同的新加速度样本；当前实验不满足。

建议与厂商确认如下接口设计，**这是建议的新协议，不是现有 selector 的说明**：

| 批量周期 | 加速度样本数 | 陀螺仪样本数 | 轴值字节数 | 主机读取频率 |
| --- | ---: | ---: | ---: | ---: |
| 10 ms | 8 | 4 | 72 | 100 次/s |
| 20 ms | 16 | 8 | 144 | 50 次/s |

每包另带协议版本、实际样本数、每个流首样本序号、硬件时钟计数/步长、溢出累计值和视频帧关联。批次边界与采样时钟不整除时允许可变样本数，不能在主机硬凑 8/4。FIFO 应规定容量和消费语义；例如覆盖 100 ms 主机暂停至少需要容纳 80 个加速度和 40 个陀螺仪样本，并留调度余量。恢复后要能持续读取积压批次。

如果厂商已有相应 XU 控制或 SDK，只需按真实协议接入并验证；若没有，则需相机固件从 IMU FIFO/数据就绪读取完整样本、加硬件时间戳，再通过合适长度的 XU 批量控制或专用 USB 数据端点送出。RDK 业务固件的修改无法自行恢复相机 MCU 已覆盖的历史数据。

### 7.3 当相机固件不能配合时

只有在取得板级原理图、IMU 型号和总线主控约束后，才能判断能否通过引出的接口直接读取 IMU。不能假设 RDK 的 I²C 能访问相机内部 I²C，也不能让两个主控直接争用总线。

如果没有可用的内部读取路径，独立 IMU 是另一种工程方案，但会引入安装外参、独立时钟、采样时间和视频同步标定工作。它不是把当前 27 字节接口的轮询频率调高即可完成的替代。

TRIG 外触发控制的是视频曝光时机，不能增加 27 字节包的容量，也不能补出被覆盖的 IMU 样本。后续若要精确融合，可以让视频曝光和 IMU 硬件时钟建立关联；采样完整性仍需先解决。

## 8. 给厂商的最小问题清单

可直接把本机 VID:PID、`bcdDevice=0701`、本报告同帧号变化样例一起发给厂商，并询问：

1. 本型号、本固件版本的 IMU 芯片具体型号、实际 ODR/量程/滤波配置是什么？800/400 Hz 是芯片内部 ODR 还是承诺上位机无丢失获得的速率？
2. selector 1 的两组数据到底是两个采样时刻、两个缓存、FIFO 两条记录还是其他含义？每组加速度和角速度是否各自有新数据有效标志？
3. 为什么同一个三字节帧计数器下 IMU 载荷持续变化？这三字节关联曝光开始、曝光结束、视频打包还是别的时刻？
4. unit 3 的 selector 2、3，以及 unit 4 的完整控制定义是什么？是否有 ODR、FIFO、批量大小、数据就绪/溢出查询开关？
5. 可提供哪一份 Linux SDK/源码和适配固件？需要能无丢失获取 800 Hz 加速度与 400 Hz 陀螺仪的最小样例及原始日志，而不只是 Windows 界面刷新截图。
6. 是否提供每轴独立采样序号/硬件时间戳、时钟频率及回绕规则？暂停主机读取 100 ms 后，如何取回全部积压数据、判断 FIFO 溢出？
7. 若需新固件，能否提供上述 10/20 ms 批量协议，以及与视频帧序号/曝光事件的硬件时间关联？

本轮没有代发消息；这里只准备技术沟通材料。

## 9. 后续验收：什么证据才可以宣布达标

1. **配置证据：** 芯片身份、实际 ODR/量程/滤波寄存器或厂商可验证的等价查询。
2. **完整性证据：** 加速度、角速度各自连续样本序号，FIFO 溢出计数；无丢样应由这些字段证明。30 分钟名义数量约为 1,440,000 个加速度向量、720,000 个角速度向量，实际应按硬件采样时钟、首尾时间和频差判断，不能强行凑整数。
3. **暂停恢复：** 主机暂停 100 ms 后能取回约 80/40 个积压样本；暂停超过容量时明确报告溢出和缺口。
4. **时序证据：** 硬件采样间隔名义为 1.25/2.5 ms，记录时钟频差和每批传输延迟；不把 GET_CUR 主机中点作为精确样本时间。
5. **真实负载：** 与双目视频编码、音频、写盘同时连续运行，检查采集队列、完整性、退出/恢复和下游读者；本轮短探针实验不替代该阶段。
6. **物理同步：** 完整采样验收通过后，再通过可观察的运动/光学事件及时间/空间标定验证 IMU 与相机的关联。音视频已经校准，不代表 IMU 自动校准。

## 11. 第二轮真机调试：继续定位恢复标称的阻塞点

### 11.1 USB 请求实际等待时间

设备内核为 `6.1.83`，支持可加载的 `usbmon`，未启用 FTRACE。临时加载 usbmon，利用已挂载的 debugfs 记录总线 1 上相机 EP0 控制传输；仅将本相机控制请求写入日志，实验完成后卸载该模块。

C 探针连续 5 秒读取 1,017 次，USB 跟踪中完整匹配到 1,017 对提交/完成事件，每次均为 unit 3、selector 1、GET_CUR、27 字节。

| 区间 | 最小/µs | 中位数/µs | 平均/µs | 最大/µs |
| --- | ---: | ---: | ---: | ---: |
| 请求提交 → 完成回调 | 3,525 | 4,734 | 4,886.271 | 6,444 |
| 上一请求完成 → 下一请求提交 | 17 | 28 | 34.235 | 636 |

约 99.3% 的请求周期发生在 USB 请求提交之后。把主机间隙完全消除，按这个实验也只会从约 203 次/s 提高至约 205 次/s，距离需要的 400 次/s 很远。追踪未发现每次 GET_CUR 前额外查询 GET_LEN/GET_INFO 的冗余。

这把限制定位到应用循环以下，但**不能直接把 4.886 ms 全算成 IMU 芯片或相机 MCU 的处理时间**。usbmon 记录驱动向主机控制器提交的请求及其回调，仍包含主机控制器调度、总线事务和设备等待；它不是电气总线分析仪。[Linux usbmon 官方文档](https://www.kernel.org/doc/html/latest/usb/usbmon.html)

### 11.2 并发读取能否突破限制

每个进程单独打开 `/dev/video0`，使用同一已知 GET_CUR。每轮运行约 6 秒，所有响应在内存缓存后保存；总吞吐使用全部进程的最早请求起点到最晚请求终点计算。

| 并发进程数 | 总响应数 | 总观察区间/s | 合计读取次数/s |
| ---: | ---: | ---: | ---: |
| 1 | 1,220 | 6.003818 | 203.204 |
| 2 | 1,221 | 6.009057 | 203.193 |
| 4 | 1,223 | 6.019615 | 203.169 |
| 8 | 1,228 | 6.042180 | 203.238 |

增加读取进程只分摊现有吞吐，没有提高总读取量。当前 Linux UVC 路径不能靠多线程/多 FD 解决目标速率问题。每路观测会相互交错，因此这些并发文件只用于链路诊断，不能拼接后未经协议验证就作为无丢失样本序列。

### 11.3 检查帧头和 JPEG 内部是否有第二条 IMU 通道

设备存在 `/dev/video1`，格式 `UVCH`，为 UVC Payload Header Metadata 节点。直接采集 120 个视频帧对应的元数据，取得 354,376 字节，成功解析 16,108 个头记录：

- 全部 UVC 头长度为 12 字节，除主机时间/SOF 包装外，只包含标准头标志、PTS 和 SCR 字段。
- PTS 不同值共 120 个，没有额外私有头字节可承载本次寻找的 IMU 样本批次。
- 解析消费全部字节，无尾部未解析数据。

随后暂时停止业务服务，直接从 `/dev/video0` 保存 16 个原始 MJPG 帧，绕过业务 JPEG 裁切和编码。16 帧均无 SOI 前缀、EOI 后缀或帧间附加数据；APP0 为 AVI1 及递增字段，APP1 为 6 字节全零。未发现包含完整六轴批次的额外 JPEG 标记段。

上述结果只说明**当前模式下已检查的帧头和显式 JPEG 元数据中没有找到这条通道**，不能排除私有模式、尚未启用的扩展或未公开的编码方式。原始图像与所有解析结果保留供厂商对照。

### 11.4 真正高帧率的手动短曝光实验

第一轮自动曝光下，120/210/570 fps 参数没有转化为对应实际帧率。第二轮查询确认：`auto_exposure=3`、`exposure_time_absolute=166`、`power_line_frequency=2`。

使用相机公开的标准 V4L2 控制，临时切换 `auto_exposure=1`，把曝光设为允许的最小值 `exposure_time_absolute=3`（名义 0.3 ms），关闭防闪烁限制 `power_line_frequency=0`。每个模式预热 2 秒后，由 C 探针读取 8 秒，视频只接收、不解码。

| 视频模式 | 日志末段实收 fps | IMU 响应数 | GET_CUR 次/s |
| --- | ---: | ---: | ---: |
| 3840×1080 MJPG，60 fps | 59.83 | 1,626 | 203.158 |
| 2560×720 MJPG，120 fps | 120.01 | 1,609 | 201.096 |
| 1280×480 MJPG，210 fps | 209.80 | 1,537 | 192.069 |
| 640×240 MJPG，570 fps | 555.53 | 1,395 | 174.244 |

短曝光下高帧率确实显著提高，补足了第一轮的重要对照；IMU 接口却随视频吞吐增加而变慢，仍达不到目标。不能把 555.53 fps 报成实测 570 fps，也不能由此判断传感器内部 IMU ODR。

该实验是临时低曝光诊断，不是推荐生产画质配置。最后恢复 MJPG 3840×1080、60 fps，恢复原曝光值 166、自动曝光 3、防闪烁 2，并重新启动业务服务。配置文件 SHA 和业务版本均与实验前相同。

### 11.5 控制现值和厂商资料的新线索

公开资料已定位到英龙信官方 [YLX-2UQ2 产品页](https://www.seecapx.com/cn/products/220global-binocular-camera.html)。型号、USB2.0 和系列视频模式与设备有对应关系。其规格图仅笼统描述 IMU 与视频同步输出，没有给出具体 IMU 型号、ODR 配置、FIFO 协议或完整 800/400 Hz 上位机输出的验收条件，不能替代本设备适配协议。规格图保存在证据目录的 `vendor-product.jpg`。

另外，UVCXU 名称对应的原作者公开说明是通用 XU 调试工具，允许使用者自行选择 GUID/selector 并执行 GET/SET，工具名称本身不能作为这台相机完整高频 SDK 的证据。[UVCXU 原作者说明](https://www.usbzh.com/article/detail-761.html)

**目前的实际阻塞是：没有可验证的 IMU 型号/ODR 查询、FIFO 消费协议或相机固件源码，无法把“恢复到标称”转化为有依据的设备配置操作。** 也没有已有 800/400 Hz 完整输出的历史记录可证明某项配置曾被降低。此前已知的软件过滤问题仍成立，但修正它只能保留更多当前响应，不能填补本轮已测出的输出数量缺口。

下一步需要厂商提供本型号、本相机固件版本适用的 Linux 库/源码包及完整 XU 协议，或提供可批量输出并附样本序号/硬件时间的相机固件。已向用户请求资料路径/链接。未取得协议前，不通过猜测私有 selector 写值、插值、重复数据或伪造时间戳宣称恢复成功。
