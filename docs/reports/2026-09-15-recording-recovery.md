## 原始故障与设计缺口

2026-09-15 的两次 `fanfan` 录制分别为：

旧版本已经按小段写视频，但把“可以正常下载的封存结果”绑定到了整个会话成功结束：完整分段记录只在进程内保存；失败后留下 `.partial`，没有生成可用前段的独立清单；启动恢复只处理已存在完整 `manifest.json` 且控制文件已移除的最后重命名阶段。因此，磁盘上存在完整分段，产品仍把整次录制显示为失败，普通导出无法访问这些分段。修复前的这一启动恢复逻辑可追溯到 Conductor 初始导入 `9986dcf`，不能据此归因于最近一次修改。

旧日志证明音频写盘存在明显长尾：两次录制的最长 `fsync` 分别约 5.359 秒和 2.899 秒。旧视频编码输出线程持有 VPU 输出缓冲调用同步写盘，磁盘阻塞可沿编码流水线传播。旧固件没有区分相机输入缺帧和应用队列拒收，不能把上述两次缺口都确定归因于磁盘。

两个原始会话已提前完成尽可能完整的恢复导出，包含可解码尾段、原始源文件和校验记录，位于工作站 `/home/alpen/OpenAria Exports/YLX-8E8AFA81/`。本次修复不修改这两个会话的原始媒体。

## 实现

- 每对双目视频完成 MP4 关闭、文件及目录同步后，核实帧索引已覆盖该分段，再原子写入 `segments.json`。录制开始时持久保存配置、会话计划和单调时钟原点。
- 音频磁盘线程在每个完整 WAV 段关闭后提交检查点，包含样本范围和实际 ALSA 硬件时钟观测。音频采集线程不承担检查点写盘。
- 运行时失败先尝试排空已接收的视频和音频，再校验连续完整前段并生成正常的会话清单。源缺帧不再导致已经完成的前段从普通下载入口消失。
- 启动恢复可在没有进程内状态时执行，并覆盖清单写入、控制文件归档和目录发布之间的中断。恢复后再次启动不会重复生成会话。
- 恢复仅引用完整双目分段。坏哈希、缺一只眼、缺帧索引、损坏 JSON 行或不安全路径会限制可发布的连续前段。原始索引和不完整尾段保留；帧索引、IMU 前缀和必要的末段音频裁剪写入独立 `recovery/` 目录。
- 音频能通过硬件时钟连续性验证时一并保留；无法证明有效时明确记录未恢复音频及原因，继续保留有效视频。
- 编码器输出线程复制压缩包后立即释放 VPU 缓冲，由每只眼独立的有界队列和写盘线程处理文件 I/O。队列同时限制字节数与帧数，包括正在写入的包；容量耗尽明确报错。
- 双眼完成事件按分段序号配对，允许左、右封存速度不同，避免快眼完成多个段时旧的单槽记录被覆盖。文件或目录 `fsync` 失败不会宣布该分段已完成。
- 保存相机队列、写盘队列、单次写入与封段耗时；源缺口区分相机输入和应用拒收，并记录近 64 帧的取帧间隔、控制操作及读取耗时。
- 恢复清单中的中断回执参与 Python 和 Rust 的 artifact 索引、完整性校验及正常下载。界面显示“录制已中断，已保存前 … 秒，可导出”，并保留原始失败诊断。
